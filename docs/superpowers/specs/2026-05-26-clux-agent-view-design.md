## Problem

clux delivers tmux notifications when a Claude Code session finishes or needs input. It works for **interactive** sessions because its hook (`notify-tmux.sh`) runs inside a process that has `$TMUX`/`$TMUX_PANE`, lets it map the event to a tmux pane, write a queue entry, and ring the bell.

Claude Code's **agent view** (`claude agents`, research preview, v2.1.139+, observed v2.1.150) breaks that assumption. Each row is a **background session** hosted by a per-user supervisor process, **detached from any terminal**. When such a session needs attention, its hook still fires — but in a process with **no `$TMUX`**, so clux's current script bails at `[ -n "$TMUX" ] || exit 0` (`notify-tmux.sh:41`) and nothing is shown. There is also no tmux window to "arrive at," so auto-dismiss-on-arrival never triggers.

Root cause is the **delivery/navigation mechanism**, not the hook choice — `Notification` is the correct event for "needs attention." Official docs confirm "Hooks run without a controlling terminal, so writing escape sequences directly to `/dev/tty` fails," which is exactly why the new `terminalSequence` hook-output field exists.

## Goal

Surface agent-view background sessions that need attention in clux's existing notification stream — visual (status bar) + sound + an instant desktop ping — and let the user jump to their running `claude agents` dashboard, while clearing each notification precisely when its session is attended to.

Non-goal (v1): replacing or duplicating agent view's own UI; tracking working/completed states; pinpointing a specific row inside the dashboard.

## Verified facts (sources)

- Agent view: `claude agents`, research preview, requires v2.1.139+. Background sessions run under a per-user supervisor, "a full Claude Code conversation with its skills, hooks, MCPs, permissions," detached from the terminal. — https://code.claude.com/docs/en/agent-view
- Dashboard sets its terminal title to e.g. `2 awaiting input · claude agents` (user-confirmed real value: `2 awaiting input · claude agents │ 2.1.150`). — agent-view docs + user observation
- `Notification` hook matches notification types `permission_prompt`, `idle_prompt`, `auth_success`, `elicitation_dialog`, `elicitation_complete`, `elicitation_response`. — https://code.claude.com/docs/en/hooks
- `terminalSequence` hook-output field (v2.1.141+): "return the escape sequence … and Claude Code emits it for you through its own terminal write path. This is race-free, works inside tmux and GNU screen, and works on Windows." Allowed: OSC `0/1/2` (titles), OSC `9` (iTerm2/ConEmu/Windows Terminal/WezTerm), OSC `99` (Kitty), OSC `777` (urxvt/Ghostty/Warp), bare BEL. — hooks docs
- `session_id` is a common input field on all hook events (enables clear-by-id). — hooks docs
- Dashboard filter `s:blocked` shows "everything waiting on you" (noted; not used in v1). — agent-view docs

## Design

### Principle: one hook, two branches, one shared queue

The existing `notify-tmux.sh` continues to handle every event, branching on `$TMUX`:

```
Claude hook fires (Notification / Stop / UserPromptSubmit / SessionEnd)
        │
        ├─ $TMUX set  → INTERACTIVE PATH  (unchanged)
        │                 queue line:  SESSION:WINDOW msg|||session_id:window_id
        │
        └─ $TMUX unset → AGENT PATH  (new)
                          on Notification(permission_prompt|idle_prompt):
                              fire desktop ping DIRECTLY (osascript / terminal-notifier)
                              also emit terminalSequence (BEL + OSC) as a bonus
                              append queue line:  ⚡ <label> <msg>|||agent:<claude_session_id>
                          on UserPromptSubmit | Stop | SessionEnd:
                              remove queue line matching |||agent:<claude_session_id>
```

Both paths append to the **same** queue file. The agent path resolves that path from `$CLUX_NOTIFY_FILE` → a HOME-derived sidecar file → the `$HOME` default **only** (never `tmux show-option`), because a detached hook may have no reachable tmux server — see §"Queue-file path resolution". The write is a plain file append, valid without tmux. The status bar (which has tmux context) renders the mixed queue.

### 1. Trigger

- **Event:** `Notification`, types `permission_prompt` and `idle_prompt` only. Other types ignored in v1. (Prototype confirmed both the event and a populated `notification_type` field fire in a detached bg session — see "Prototype findings".)
- **`notification_type` parsing:** with `jq`, read the `notification_type` field and act only on `permission_prompt`/`idle_prompt`. In the **grep fallback (no `jq`)**, the agent path does NOT attempt to parse `notification_type` (the JSON-via-grep extraction is unreliable for it); instead it treats **any** detached `Notification` as eligible and proceeds — the excluded types (`auth_success`, `elicitation_*`) are unlikely to arise in a background session, so the precision loss is acceptable and is documented. [inferred] When `notification_type` is absent or unparseable, default to eligible (treat as needs-input). [inferred]
- **Agent-path config resolution (no tmux):** because `tmux show-option` returns empty in a detached hook, the `@clux-agent-*` options can NOT be read in the agent path. For v1, **all agent-path behavior is hardcoded to the documented defaults** (visual on, sound on, desktop on, OSC `9`, marker `⚡`); the `@clux-agent-*` tmux options (§5) only affect the **reader/jump side**, which has a tmux server. [inferred] Persisting these options to a HOME-derived sidecar env file for the agent path is a documented future enhancement, not v1. [inferred]
- **Instant ping (primary, detached-safe):** the hook fires a desktop notification **directly** — `osascript -e 'display notification …'` on macOS, falling back to `terminal-notifier` if present; Linux can use `notify-send`. This is the load-bearing path because a fully detached agent session has **no terminal**, so an emitted `terminalSequence` has nowhere to land. In the agent path this is gated by the **hardcoded default** of `@clux-agent-desktop` (on), since the tmux option can't be read detached. [inferred] **Sound mechanism (explicit):** the agent path **REUSES the existing line-38 `notify-sound.sh "$TYPE"` invocation** rather than firing its own sound — it already runs unconditionally in both paths before the `$TMUX` guard. [inferred] Because `notify-sound.sh` sources `helpers.sh` and reads sound-enabled via `tmux show-option` (which returns empty when detached), the decision falls through to `_get_notification_default_sound`, which yields **"on" only for type `notification`** and "off" otherwise; this maps to the desired per-event behavior with **no special-casing**: agent `Notification` (→ type `notification`) plays a sound, while agent `UserPromptSubmit`/`Stop`/`SessionEnd` (silent clears) play nothing. [inferred] The sound decision therefore must NOT depend on any tmux value; `notify-sound.sh`'s detached `tmux` calls — specifically, the `tmux show-option` IPC triggered at notify-sound.sh line 14 (which sources helpers.sh, triggering its module-level get_tmux_option calls at helpers.sh lines 14-18) [inferred] — are harmless (they return empty and the defaults take over), but the agent-path sound behavior is defined entirely by `map_event_to_type` + `_get_notification_default_sound`, not by tmux state. [inferred] (The `@clux-agent-sound` default of "on" in §5 governs the reader-side concept of agent sound; the actual writer-path sound is the line-38 call described here, and the two are consistent for the `Notification` event.) [inferred]
- **Instant ping (bonus, attached/peek only):** the hook *also* prints JSON `{ "terminalSequence": "<seq>" }` — a bare BEL plus **one** desktop-notification OSC — so that if the session happens to be attached or peeked in a terminal, that terminal also surfaces it. The OSC code uses the **hardcoded default** `9` in the agent path (broadest coverage: iTerm2/WezTerm/Windows Terminal/ConEmu), since `@clux-agent-osc` can't be read detached; users on Kitty (`99`) or Ghostty/Warp/urxvt (`777`) would need the future sidecar-config enhancement to override it. [inferred] Emitting a single code avoids double notifications on terminals that support several. This path is best-effort and **never** the sole notification; the direct desktop ping above always fires.
- **`terminalSequence` literal payload + sanitization:** the JSON object printed on stdout is exactly `{"terminalSequence":"<seq>"}` and nothing else — hook-output parsing breaks on stray stdout, so the agent path must NOT echo any other text to stdout (logging goes to stderr or a file). [inferred] The `<seq>` value is, for the default OSC `9`: a bare BEL (`\a`) followed by `ESC ] 9 ; <text> BEL` (i.e. `\x1b]9;<text>\a`); for OSC `99` (Kitty) and `777` (urxvt/Ghostty/Warp) the same `ESC ] <code> ; <text>` form is used, terminated with BEL (`\a`) rather than ST for consistency. [inferred] `<text>` is a short fixed payload (e.g. `Claude: <label>`); before embedding, both the interpolated `<label>` and any message are **sanitized** by stripping control characters (including embedded `ESC`/BEL/`\r`/`\n`) and escaping `"` and `\` for the JSON string context, so a malicious or odd payload cannot corrupt the OSC or the surrounding JSON. [inferred] **Sanitization applies to the post-extraction value in BOTH paths** — i.e. whatever `<label>` ends up being (the `jq`-decoded `message` in the jq path, or the grep-extracted value in the no-jq path, which the line-19 `grep -o '"message":"[^"]*"'` truncates at the first embedded quote) is sanitized after extraction, so the grep path can only ever produce a lossy-but-safe label, never an unsanitized one. [inferred] Whether to additionally write a raw BEL to the tty is moot in the detached path (no tty); the BEL is carried inside `terminalSequence` only. [inferred]
- **Queue entry:** append `⚡ <label> <msg>|||agent:<claude_session_id>` with **dedup** on `agent:<session_id>` (same intent as today's per-context dedup) so one session can't stack duplicates.
- **`<label>` (v1):** the hook payload `message`, or the literal `needs input` when `message` is empty. Enriching the label with the session name via a one-shot `claude agents --json` lookup is a documented future enhancement, not v1.

### 2. Show

- `show-notification.sh` is effectively unchanged: it already renders `${line%%|||*}`, so `⚡ <label> <msg>` displays directly, and the `[1/N]` counter already spans the mixed queue.
- The auto-dismiss-on-arrival block only matches tmux `session_id:window_id`; `agent:` entries never match a focused window, so they persist until cleared by hook or manual dismiss. **No code change required there** beyond confirming `agent:` lines fall through the existing branches harmlessly.

### 3. Navigate

`jump-to-notification.sh` gains a branch when the top entry's id field begins with `agent:`:

```
match = tmux list-panes -a -F '#{session_id}\t#{window_id}\t#{pane_title}'
          | grep -F 'claude agents' | head -1
if match:  read session_id, window_id from match
           tmux switch-client -t "$session_id"  &&  tmux select-window -t "$window_id"
else:      tmux new-window -n agents "claude agents"   # fallback: no dashboard open
```

The capture format is `#{session_id}\t#{window_id}\t#{pane_title}` so that `switch-client` has the **session** (the original pseudo-code captured only `window_id`, which is insufficient to switch clients across sessions). [inferred] The **authoritative match field is `#{pane_title}`** — the dashboard runs as a foreground process in a pane and sets a pane title clux can match; `#{pane_current_command}`/`#{pane_start_command}` (e.g. matching the `claude` command) are noted as fallback discriminators if the title match proves unreliable. [inferred] **B10 (does `claude agents` actually set a matchable `#{pane_title}` in a tmux pane?) is UNVERIFIED and must be confirmed before locking the plan** — the prototype had no dashboard open. [inferred]

This dashboard-detect-and-jump logic is factored into a single shared helper — `agent_jump()` in `plugins/clux/scripts/helpers.sh` — so both `jump-to-notification.sh` and `notification-picker.sh` (§4) call the same code path rather than duplicating it. [inferred] In `jump-to-notification.sh` the agent-id check (the id field after `|||` begins with `agent:`) **must be evaluated BEFORE** the existing generic `*"|||"*` `session_id:window_id` parse — an `agent:` queue line also contains `|||`, so the generic branch would otherwise catch it first and mis-route the jump through the interactive `select-window -t "agent:<sid>"` path. [inferred]

No bulk clearing on jump (superseded by precise per-session clearing). Interactive entries keep their existing jump behavior.

### 4. Dismiss (precise, per session)

- **Add** on `Notification(permission_prompt|idle_prompt)` — agent path.
- **Remove** the entry whose id is `agent:<session_id>` on that session's `UserPromptSubmit`, `Stop`, or `SessionEnd` — agent path. In the agent path, `Stop` therefore **clears** rather than adding a "completed" entry (consistent with needs-input-only v1).
- **Manual fallback:** existing dismiss key and fzf picker `Ctrl-D` continue to remove any line, including `agent:` ones (needed for sessions that die without a clean hook).
- **Picker ENTER on an `agent:` line:** the picker ENTER branch parses a bare `SESSION:WINDOW` and works correctly for interactive lines (their session/window names contain no `|||`) [inferred], but would mis-parse an `agent:` line because the `⚡` label prefix does not begin with `SESSION:`. [inferred] For v1, ENTER on a selected `agent:` line is **routed through the same agent-jump logic as §3** by calling the shared `agent_jump()` helper (dashboard pane detection + fallback), not through the `SESSION:WINDOW` jump; the picker detects the `agent:` id prefix and dispatches accordingly. [inferred] Because `notification-picker.sh` is self-contained and does **not** source `jump-to-notification.sh`, the §3 detect-and-jump logic is extracted into `agent_jump()` in `plugins/clux/scripts/helpers.sh` (a single shared definition both scripts source) rather than duplicated in the picker. [inferred] (`jump-to-notification.sh` itself still acts only on the TOP line; the picker can select any line, so the picker's ENTER handler performs the prefix check before deciding which jump path to take.) [inferred]
- **Removal/dedup helper:** removal and dedup are done by a single helper that **must `acquire_lock`** first, filters the queue with `grep -vF` against the full `|||agent:<session_id>` token **anchored to end-of-line** (the id field is always the trailing segment of a queue line, so `grep -vF "...|||agent:${sid}$"`-style end-anchoring prevents a session id from matching as a prefix of a longer id), then **atomic-replaces** the queue file and calls `release_lock`. [inferred] Dedup-on-add uses the **same** end-anchored `|||agent:<session_id>` token so add and remove can never target different lines. [inferred] (`grep -F` is literal; if end-anchoring with `-F` is awkward, the helper may match the literal token and assert it is the line suffix — document whichever form is used.) [inferred]

### 5. Config (new tmux options, optional, mirroring helpers.sh patterns)

**Applicability (v1):** these options are read via `tmux show-option`, which returns empty in a detached agent hook, so they govern only the **reader/jump side** (status-bar rendering, the jump branch, the manual picker) that has a tmux server. The **agent (writer) path uses the hardcoded defaults** below and ignores any custom values; honoring them in the agent path requires the future HOME-derived sidecar-config enhancement. [inferred] **Single source of truth:** the agent-path hardcoded constants stated in §1 prose (visual on, sound on, desktop on, OSC `9`, marker `⚡`) and the defaults in this §5 table are the **same values** and must be kept in sync — when one changes the other must be updated in lockstep (this table is the canonical reference). [inferred]

| Option | Default | Meaning |
|---|---|---|
| `@clux-agent-visual` | `on` | show ⚡ entries in the status bar |
| `@clux-agent-sound` | `on` | play the notification sound (system / `notify-sound.sh`) and BEL |
| `@clux-agent-desktop` | `on` | fire a **direct** OS desktop notification (osascript / terminal-notifier / notify-send) |
| `@clux-agent-osc` | `9` | OSC code for the **bonus** terminalSequence ping (`9`, `99`, or `777`); attached/peek only |
| `@clux-agent-marker` | `⚡` | glyph prefixing agent entries |

Sound file selection reuses the existing per-type config in `helpers.sh`.

### Queue-file path resolution (hardened)

`helpers.sh` currently derives `NOTIFY_FILE` from `tmux show-option -gqv @claude-notify-file`, while `show-notification.sh` (the status-bar reader) derives it from `$CLUX_NOTIFY_FILE` / `$HOME`. The prototype confirmed a detached hook's `tmux show-option` returns empty at exit 0, so in **default** config both fall through to the same `$HOME/.config/tmux/claude_notification` and they agree. But the divergence is latent: a user who sets `@claude-notify-file` would silently split the writer (hook) and reader (status bar) paths in the agent context.

**Resolution:** the **agent path must resolve the queue file from `$CLUX_NOTIFY_FILE` → a HOME-derived sidecar file → the `$HOME` default — never from `tmux show-option`** — so it can't depend on a reachable tmux server and still honors a custom `@claude-notify-file`. (The interactive path keeps its existing resolution; it always has a tmux server.) Factor a single `resolve_notify_file()` helper that both the hook and `show-notification.sh` use, so writer and reader can never diverge.

**Why the sidecar tier exists (CRITICAL fix):** `$CLUX_NOTIFY_FILE` is populated only via `tmux setenv -g` (`claude-notify.tmux:13`), which a detached agent hook does **not** inherit, so in the agent path `$CLUX_NOTIFY_FILE` is almost always empty. [inferred] Without an intermediate tier, a user who set `@claude-notify-file` to a custom path would split the writer (agent hook, falls through to the `$HOME` default) from the reader (status bar, has tmux env, resolves the custom path) — the "never diverge" guarantee would fail for any non-default config. [inferred] **To preserve the guarantee, `claude-notify.tmux` writes the resolved queue-file path at plugin load time to a fixed HOME-derived sidecar** (e.g. `~/.config/clux/notify-file-path`), and `resolve_notify_file()` reads the tiers in order: `$CLUX_NOTIFY_FILE` → sidecar file → `$HOME` default. [inferred] (Simpler fallback if the sidecar is rejected: explicitly scope v1 to "custom `@claude-notify-file` is unsupported for agent sessions" and assert/document that the agent path uses the `$HOME` default only — but the sidecar is the chosen primary fix because it keeps custom configs working.) [inferred]

`resolve_notify_file()` must be a **pure path-resolution function with no top-level `tmux show-option` side effects** (it only reads env vars, the sidecar file, and the `$HOME` default), so `show-notification.sh` can adopt it without incurring per-status-redraw tmux IPC. [inferred] **Sharing mechanism (CRITICAL — do NOT source `helpers.sh` from `show-notification.sh`):** `helpers.sh` runs module-level `tmux show-option` IPC at source time (≈lines 14-18, plus `LOCKDIR=` at ≈line 88), and `show-notification.sh` does **not** currently source it; sourcing `helpers.sh` merely to obtain `resolve_notify_file()` would trigger that top-level IPC on every status redraw, contradicting "no IPC per redraw." [inferred] Therefore `resolve_notify_file()` (and only it) lives in a **new side-effect-free file** — `scripts/path.sh` — that contains zero top-level statements (function definitions only); both the hook and `show-notification.sh` source `path.sh` directly, while `helpers.sh` may also source `path.sh` so writer and reader still share one definition. [inferred]

### Error handling / edge cases

- **No `jq`:** existing grep fallback in `notify-tmux.sh` must also parse `session_id`; agent path degrades gracefully (skip dedup precision, still add/remove best-effort). The grep fallback does **not** parse `notification_type` (unreliable via grep) and instead treats any detached `Notification` as eligible — the excluded types are unlikely in a bg session, so the precision loss is acceptable and documented. [inferred] **`session_id` reliability contract (no-jq):** `session_id` is a UUID-form string with no embedded quotes, so a `grep -o '"session_id":"[^"]*"'` extraction is reliable when the field is present — unlike `message`, it does not suffer the embedded-quote truncation. [inferred] **Reliable dedup AND clear-by-id therefore work in the no-jq path whenever a clean `session_id` is extracted** (the add and remove keys are built from the same extracted value via the same end-anchored `|||agent:<session_id>` token, so they target the same line — the "add and remove can never target different lines" guarantee holds, since both derive from one extraction). ## Prototype findings (validated 2026-05-26)

A throwaway probe (`claude --bg` a task forced into a permission prompt, with a logging hook) settled the load-bearing assumptions. Artifacts deleted after the run.

- **A1 (critical) — CONFIRMED:** `Notification` fires in a detached bg session with `notification_type=permission_prompt`, `message="Claude needs your permission"`, `status=waiting`. The hook-driven trigger works; **the `claude agents --json` poller fallback is not needed.** `SessionStart`/`UserPromptSubmit`/`Stop` also fire (lifecycle add/clear works).
- **A1 caveat — `terminalSequence` is NOT detached-safe:** a fully detached session has no terminal write path, so the emitted OSC almost certainly does not surface. **This is why the spec now fires the desktop ping directly (§1) and keeps `terminalSequence` only as an attached/peek bonus.**
- **A2 — CONFIRMED:** the bg-session hook has `TMUX`/`TMUX_PANE` **unset** in every invocation → reliable branch discriminator.
- **A3 — CONFIRMED (add/clear):** `UserPromptSubmit` and `Stop` fire in the bg session with a **stable, identical `session_id`** across events → dedup and clear-by-id are sound.
- **Environment — CONFIRMED:** bg hook sees `HOME=/Users/jazz` (same as the reader) and can write `~/.config/tmux/`; `tmux show-option` returns empty at exit 0 (no hang); `jq` present, `flock` absent (macOS uses the `mkdir` lock path).

**Not exercised by the prototype (carried into the plan as tests):** B7 (grep fallback without `jq`), B8/B9 (lock/concurrency on the `mkdir` path), B10 (dashboard-pane detection with a dashboard actually open).

Full verdict: **SUCCESS** → ready for `writing-plans`, with the `terminalSequence`→direct-OS-notification and queue-path-pinning refinements folded in above.
